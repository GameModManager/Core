# Backup and restore points: design

Status: design only. No production code has been written against this document.

Scope: timestamped backup and restore of a profile's load order and mod list.
Reference behaviour is Mod Organizer's, read from
`references/modorganizer` and `references/modorganizer-game_bethesda`. That
source is GPL-3 and is read for behaviour only. Nothing in it is copied.

---

## 1. What MO2 actually does

Sources are the MO2 checkout at `references/modorganizer` and the Bethesda
game plugin at `references/modorganizer-game_bethesda`.

### 1.1 What is in the reference, and what is not

MO2's backup path calls five functions that live in **MOBase / `uibase`**,
which is a separate package and is **not vendored under `references/`**
(`src/CMakeLists.txt:7` does `find_package(mo2-uibase CONFIG REQUIRED)`):

| Function | Status |
|---|---|
| `shellCopy` | uibase, not vendored |
| `removeOldFiles` | uibase, not vendored |
| `SelectionDialog` | uibase, not vendored |
| `SafeWriteFile` | uibase, not vendored |
| `formatSystemMessage` | uibase, not vendored |

Everything below is cited to a line in the vendored MO2 sources. Where a claim
rests on a uibase function's behaviour rather than on MO2's call site, that is
stated explicitly.

### 1.2 The backup format

**MO2's backup is a byte-for-byte file copy. It is not a re-serialisation.**
`MainWindow::createBackup` (`mainwindow.cpp:3828-3839`) builds the destination
name and then calls `shellCopy` on the live file (`mainwindow.cpp:3831`).
Whatever the live writer happened to produce is what lands on disk, verbatim.

The load-order backup copies three files from the current profile directory
(`mainwindow.cpp:3845-3847`), all named by `Profile::get*FileName()`:

| File | Accessor | Cite |
|---|---|---|
| `plugins.txt` | `Profile::getPluginsFileName()` | `profile.cpp:948-951` |
| `loadorder.txt` | `Profile::getLoadOrderFileName()` | `profile.cpp:953-956` |
| `lockedorder.txt` | `Profile::getLockedOrderFileName()` | `profile.cpp:958-961` |

The mod-list backup copies one file (`mainwindow.cpp:3922`):

| File | Accessor | Cite |
|---|---|---|
| `modlist.txt` | `Profile::getModlistFileName()` | `profile.cpp:943-946` |

Because the path is built as `directory / name` (`profile.cpp:945`, `950`,
`955`, `960`), the backup lands **next to the file it copies**, inside the
profile directory.

Both handlers flush first, so the copy is of current state and not of
whatever the debounced writer last happened to emit:

- load order: `m_OrganizerCore.savePluginList()` (`mainwindow.cpp:3843`)
- mod list: `m_OrganizerCore.currentProfile()->writeModlistNow(true)`
  (`mainwindow.cpp:3920`), which is `writeImmediately(onlyIfPending)`
  (`profile.cpp:233-236`) - if nothing is pending, the on-disk file is already
  current and nothing is rewritten.

### 1.3 The formats that get copied

These are the live writers' outputs. They matter because a restore puts these
bytes back.

**`plugins.txt`** - `GamebryoGamePlugins::writePluginList` delegates to
`writeList(pluginList, filePath, /*loadOrder=*/false)`
(`gamebryogameplugins.cpp:81-85`, `93-143`):

- header `# This file was automatically generated by Mod Organizer.\r\n`
  (`gamebryogameplugins.cpp:104-105`)
- plugin names sorted by **ascending** priority
  (`gamebryogameplugins.cpp:110-114`)
- only plugins in `STATE_ACTIVE` (`gamebryogameplugins.cpp:117`)
- **system** encoding, not UTF-8 (`gamebryogameplugins.cpp:98-100`)
- CRLF line endings, no prefix characters

**`loadorder.txt`** - the same writer with `loadOrder=true`
(`gamebryogameplugins.cpp:87-91`, called from
`gamebryogameplugins.cpp:33-34`):

- same header, same ascending-priority sort
- **all** plugins regardless of state (`gamebryogameplugins.cpp:117`)
- **UTF-8** encoding (`gamebryogameplugins.cpp:98-100`)

**`lockedorder.txt`** - `PluginList::writeLockedOrder`
(`pluginlist.cpp:789-800`):

- header, then `name|priority\r\n` (`pluginlist.cpp:794-798`)
- `m_LockedOrder` is a `std::map<QString, int, FileNameComparator>`
  (`pluginlist.h:413`), so the file is sorted by **case-insensitive name**,
  not by load order.

Wiring: `OrganizerCore::savePluginList` (`organizercore.cpp:1974-1982`) calls
`PluginList::saveTo` (`pluginlist.cpp:802-810`), which asks the game feature to
write `plugins.txt` and `loadorder.txt` (`pluginlist.cpp:804-807`,
`gamebryogameplugins.cpp:32-34`) and then writes `lockedorder.txt`
(`pluginlist.cpp:809`).

**A detail worth knowing.** `PluginList::saveLoadOrder`
(`pluginlist.cpp:812-...`) does **not** write `loadorder.txt`. For games whose
load-order mechanism is `FileTime` (`pluginlist.cpp:814`) it stamps Win32
`FILETIME`s onto the ESP files instead, computed as
`(145731 + priority) * 24 * 60 * 60 * 10000000` (`pluginlist.cpp:847-848`).
For Bethesda games the text files are authoritative; for FileTime games the
file mtimes are. MO2 backs up `loadorder.txt` unconditionally either way.

**`modlist.txt`** - `Profile::doWriteModlist` (`profile.cpp:243-281`):

- header line, then one line per mod
- ordered by **descending** priority, via `m_ModIndexByPriority.crbegin()`
  (`profile.cpp:258-274`), so the first line is the highest priority
- prefix per line: `*` foreign, `+` enabled, `-` disabled
  (`profile.cpp:264-270`)
- mods with automatic priority are omitted (`profile.cpp:263`)
- CRLF line endings

So `modlist.txt` encodes **priority (as line order), the enabled flag, the
foreign flag, and the mod name.** That is the complete boundary of what the
mod-list backup captures.

### 1.4 The naming scheme

Three constants (`mainwindow.cpp:3823-3826`):

```
PATTERN_BACKUP_GLOB  = ".????_??_??_??_??_??"
PATTERN_BACKUP_REGEX = "\\.(\\d\\d\\d\\d_\\d\\d_\\d\\d_\\d\\d_\\d\\d_\\d\\d)"
PATTERN_BACKUP_DATE  = "yyyy_MM_dd_hh_mm_ss"
```

- The suffix attaches to the **full filename including its extension**
  (`mainwindow.cpp:3830`): `loadorder.txt.2026_10_02_08_45_55`.
- The clock is **local time**, `QDateTime::currentDateTime()`
  (`mainwindow.cpp:3844`, `mainwindow.cpp:3921`), captured once and reused for
  all files in one action, so the three load-order files always share a stamp.
- Retention: **10, hardcoded in code** at `mainwindow.cpp:3834`. Not a
  setting, not user-visible, no settings dialog entry.
- Eviction rule: `removeOldFiles(dir, fileName + PATTERN_BACKUP_GLOB, 10,
  QDir::Name)` (`mainwindow.cpp:3833-3834`). The sort flag is passed by the
  call site, and the other call site in MO2 passes
  `QDir::Time | QDir::Reversed` (`organizercore.cpp:517`), which shows the flag
  is honoured rather than fixed inside the uibase helper. `QDir::Name` is
  ascending, and the zero-padded fixed-width stamp makes name order equal
  chronological order, so the **oldest is evicted and the 10 newest are kept.
  The rule is by name, not by mtime.**
- The sweep runs **once per source file** (inside `createBackup`,
  `mainwindow.cpp:3833`), so the three load-order files retain 10 each,
  independently.
- The sweep uses the loose `?`-glob (`.????_??_??_??_??_??`), **not** the
  strict regex. A file such as `loadorder.txt.9999_99_99_99_99_99` matches the
  glob and is therefore eligible for eviction, but the strict regex in
  `queryRestore` will not list it. The retention rule and the listing rule do
  not use the same matcher.

### 1.5 Restore semantics

Entry points: `on_restoreButton_clicked` (`mainwindow.cpp:3897-3916`) for the
load order, `on_restoreModsButton_clicked` (`mainwindow.cpp:3927-3940`) for
the mod list. Both delegate the picker to `MainWindow::queryRestore`
(`mainwindow.cpp:3852-3895`), anchored on the **live** file
(`mainwindow.cpp:3899`, `mainwindow.cpp:3929`).

**`queryRestore` step by step:**

1. Globs `<liveFileName>.*` in the live file's directory, `QDir::Files`,
   sorted `QDir::Name` ascending (`mainwindow.cpp:3855-3857`).
2. Iterates the list in **reverse** (`mainwindow.cpp:3867`), so the dialog
   shows **newest first**.
3. Classifies each candidate by three anchored regexes
   (`mainwindow.cpp:3860-3866`):
   - strict stamp -> choice label is `time.toString()` (a localised,
     human-readable timestamp), payload is the raw captured stamp
     (`mainwindow.cpp:3871-3873`)
   - six letters `\.([A-Za-z]{6})` -> the crash-orphan branch. Label is the
     six letters; description is *"This file might be left over following a
     crash or power loss event. Check its contents before restoring."*
     (`mainwindow.cpp:3874-3878`). The in-source comment at
     `mainwindow.cpp:3862` names the cause: orphaned `SafeWriteFile`
     temporaries.
   - anything else with a `.` -> label is the raw suffix, no description
     (`mainwindow.cpp:3879-3881`). Catches hand-made copies.
4. `SelectionDialog dialog(tr("Choose backup to restore"), this)`
   (`mainwindow.cpp:3859`).
5. Zero candidates -> `QMessageBox::information(this, tr("No Backups"),
   tr("There are no backups to restore"))`, returns empty
   (`mainwindow.cpp:3884-3888`).
6. Accepted -> `dialog.getChoiceData().toString()`
   (`mainwindow.cpp:3891`). Rejected -> empty (`mainwindow.cpp:3893`).
   An empty result means the handler does nothing at all: no restore, no error,
   no message.

**The write itself**, `on_restoreButton_clicked` (`mainwindow.cpp:3897-3916`):

- The one chosen stamp is applied to **all three** files:
  `shellCopy(pluginsPath + "." + choice, pluginsPath, true, this)` and the
  same for `loadorder` and `lockedorder` (`mainwindow.cpp:3904-3906`). The
  third argument is the overwrite flag (compare the identical four-argument
  form at `mainwindow.cpp:4026`).
- **There is no confirmation prompt. The live files are overwritten silently.**
- The three copies are `||`-chained (`mainwindow.cpp:3904-3906`), so a failure
  on `plugins.txt` short-circuits and `loadorder.txt` and `lockedorder.txt`
  are left unrestored. The profile ends up mixed with no statement that it is.
- Then `m_OrganizerCore.refreshESPList(true)` runs **unconditionally**, even
  after a failure (`mainwindow.cpp:3914`).

`on_restoreModsButton_clicked` (`mainwindow.cpp:3927-3940`) is the same shape
for one file, then `m_OrganizerCore.refresh(false)` (`mainwindow.cpp:3938`).
The `false` matters: `refresh(true)` calls `writeModlistNow(true)` first
(`organizercore.cpp:1281-1283`) and would immediately overwrite the file just
restored.

**Validation: none at restore time.** The only validation is at read time, in
`PluginList::readLockedOrderFrom` (`pluginlist.cpp:697-787`), which rejects
blank and `#` lines (`pluginlist.cpp:715-716`), lines without exactly two
`|`-separated fields (`pluginlist.cpp:719-725`), and negative priorities
(`pluginlist.cpp:730-735`). It deliberately keeps a pin for a plugin that is
not currently installed so the pin survives a reinstall
(`pluginlist.cpp:738-743`), keeps a priority above the plugin count
(`pluginlist.cpp:751-755`), refuses to lock a force-loaded plugin
(`pluginlist.cpp:747-749`), and resolves slot collisions
(`pluginlist.cpp:757-768`). `plugins.txt` and `loadorder.txt` get no
validation beyond stripping blanks and comments.

**There is no pre-restore safety backup.** After a restore, the only thing
between the user and a lost state is a different entry in the picker list.

**Post-restore reload:** `refreshESPList(true)` resolves to
`m_PluginList.refresh(profileName, dirStructure, lockedOrderFileName, true)`
(`organizercore.cpp:1295-1312`). `refresh(false)` re-reads mod info from
disk, refreshes mod status, notifies the model, and rebuilds the directory
structure (`organizercore.cpp:1278-1293`).

### 1.6 The error strings, enumerated

`featuremap.md` lists "error strings" for U034. MO2 has **two** distinct
failure messages across the whole feature, and no per-file identification:

| Message | Trigger | Cite |
|---|---|---|
| `"There are no backups to restore"` (title `"No Backups"`) | the picker found zero candidates | `mainwindow.cpp:3885-3886` |
| `"Failed to restore the backup. Errorcode: %1"` (title `"Restore failed"`) | any of the `shellCopy` calls returned false | `mainwindow.cpp:3910-3912` and `mainwindow.cpp:3934-3936` |

Everything else is **silent**:

- `createBackup` returning false produces **no message at all**. The `&&`
  chain at `mainwindow.cpp:3845-3847` simply falls through to the end of the
  slot. The user clicks the button and nothing happens.
- A partial load-order restore (plugins.txt copied, loadorder.txt not) reports
  the same generic message and never says which file is now stale.
- Cancelling the picker is not an error and is not reported.
- A successful restore produces no message either: neither handler calls
  `MessageDialog`.

### 1.7 Toasts

Success only, via `MessageDialog::showMessage`:

- `"Backup of load order created"` (`mainwindow.cpp:3848`)
- `"Backup of mod list created"` (`mainwindow.cpp:3923`)

`MessageDialog` is documented in MO2's own source as a *"borderless dialog used
to display short messages that will automatically vanish after a moment"*
(`messagedialog.h:32-34`). It auto-hides on
`QTimer::singleShot(1000 + text.length() * 40)` (`messagedialog.cpp:60`) and is
positioned bottom-centre of the reference widget (`messagedialog.h:43-44`),
optionally raised to the front (`messagedialog.h:63-64`).

**Restore never toasts.** Neither restore handler calls `MessageDialog`; the
only user feedback on a successful restore is the view repopulating.

### 1.8 Trigger points: manual only

`createBackup` is called from exactly two places in the whole MO2 tree, and
both are toolbar button slots:

- `on_saveButton_clicked` (`mainwindow.cpp:3841-3850`)
- `on_saveModsButton_clicked` (`mainwindow.cpp:3918-3925`)

There is **no automatic backup**. Not before deploy, not before a profile
switch, not on launch, not on exit. Nothing in
`OrganizerCore::saveCurrentProfile` (`organizercore.cpp:1984-1994`) or
`beforeRun` (`organizercore.cpp:2001-...`) touches `createBackup`.

There is a settings getter that looks like it might be one:
`Settings::keepBackupOnInstall()` reads `General/backup_install`
(`settings.cpp:412-415`). It has **no reader anywhere in the MO2 tree** - the
only other hit is its own setter (`settings.cpp:417-420`). It is an orphaned
setting, not an automatic-backup hook, and it is not evidence of an
automatic trigger.

The four buttons are icon-only `QPushButton`s in the two tab toolbars,
positioned immediately left of each tab's "Active:" counter:

| Button | Toolbar | Neighbour | Tooltip | Icon | Cite |
|---|---|---|---|---|---|
| `saveButton` | Plugins tab | `activePluginsLabel` + `activePluginsCounter` | "Create a backup." | `:/MO/gui/backup` | `mainwindow.ui:863` |
| `restoreButton` | Plugins tab | as above | "Restore a backup." | `:/MO/gui/restore` | `mainwindow.ui:840` |
| `saveModsButton` | Mods tab | `activeModslabel` | "Create Backup" | `:/MO/gui/backup` | `mainwindow.ui:340` |
| `restoreModsButton` | Mods tab | as above | "Restore Backup..." | `:/MO/gui/restore` | `mainwindow.ui:326` |

There is no menu entry, no keyboard shortcut, and no dialog command. The four
slot names appear nowhere outside `mainwindow.h:480-483` and
`mainwindow.cpp`.

### 1.9 Multi-instance

Per profile directory, and the profile directory is what carries the instance
identity. MO2's backup path never reads an instance or profile name: it is
handed three absolute paths and copies them. Instance identity is implied by
location only, and is never written into the backup. The timestamp is the only
metadata a backup carries.

A backup of instance A is unreadable-as-a-backup if you drop it into
instance B's profile directory, but nothing in the filename or content stops
that from happening. There is no cross-profile or cross-instance picker: the
globs are anchored on the live file's own name and directory
(`mainwindow.cpp:3855`), so the picker can only ever offer siblings of the
current file.

### 1.10 What is deliberately NOT backed up

For U034 through U036, the boundary is **profile metadata files only. Four
files. Byte-for-byte copies.**

Not backed up:

- **Mod files.** No mod directory is copied by either handler.
- **`archives.txt`**, written by the profile (`profile.cpp:963-966`) and read
  back (`profile.h:207`), is in neither backup set.
- **`settings.ini`**, the profile's INI (`profile.h:212-214`).
- **The active-profile selection** and the profile's existence.
- Any archive (BSA/BA2) content, any modpack, the deploy ledger, the overwrite
  directory.

**One adjacent MO2 feature that is easy to mistake for this one.**
`ModListViewActions::createBackup` (`modlistviewactions.cpp:1041-1051`),
reached from the mod list context menu (`modlistcontextmenu.cpp:518`), copies a
mod's *whole directory* to a sibling name via
`InstallationManager::generateBackupName` (`modlistviewactions.cpp:1044-1045`)
and reports failure with `"Failed to create backup."`
(`modlistviewactions.cpp:1047`). That is mod-file backup. It is **not** part of
U034-U036, it is not timestamped, it is not in the profile directory, and it
has a different trigger. Conflating the two is the easiest way to build the
wrong thing here.

Two format differences already in our writers, both harmless and both
intentional:

- `write_game_plugins_txt` writes two different comment lines and uses `*` as
  the enable prefix rather than MO2's system encoding plus implicit state
  (`plugin_database.cpp:1097-1109`).
- `save_profile` writes three comment lines into `lockedorder.txt`
  (`plugin_database.cpp:1088-1090`) against MO2's one.

Neither matters for backup, because a backup copies bytes and never
re-serialises.

### The important consequence: no new serialiser is needed

`parse_modlist`, `serialize_modlist`, `read_locked_order`, `write_locked_order`
and the `read_lines`/`write_lines` pair (`instance_snapshot.cpp:113-175`) are
all **bypassed entirely** on the backup path. So is `Database::save_profile` on
the restore path, apart from the pre-restore flush.

A backup is:

1. call the existing writer so the live file is current,
2. append a 19-character stamp to the live file's name,
3. `std::filesystem::copy_file`.

A restore is:

1. read the chosen backup's bytes,
2. `profile::safe_write_file(live_path, bytes)`.

That is the whole of it. This is a roughly 50-line feature, not a 400-line
one, and the entire reason is that MO2's backup is a file copy.

### Must be written new

| Item | Size | Why it is unavoidable |
|---|---|---|
| `engine/backup/backup_service.{h,cpp}` | ~250 lines | The stamp, the retention sweep, the candidate classification, the per-file result enum. None of it exists. |
| Per-choice description on the picker | ~15 lines | `ListDialog` has `setChoices` + `setChoiceData` (`list_dialog.h:27-29`) but no per-item tooltip, so MO2's orphan-temporary warning (`mainwindow.cpp:3876-3877`) has nowhere to go. |
| A transient info message | ~40 lines | No `MessageDialog` equivalent exists. `engine::InAppBackend` (`notification_backend.h:17-24`) is a signal emitter with no consumer. |
| Two icon keys | asset work | `resources/icons/ACTIVE_ICONS.txt` has `save` (line 41) and nothing backup-shaped. |

## 3. Backup layout

### Paths

Backups sit beside the file they copy, inside the profile directory, which is
`<instance>/profiles/<profile>/` (`instance.cpp:157` resolves
`InstanceKind::Profiles` to the `profiles` leaf, honouring a per-instance
`profiles_dir` override). This is the same directory layout MO2 uses, and
`mo2_importer.cpp:286` reads MO2's `profiles` directory, so a user who already
has MO2 timestamps sitting next to their imported profile will see them listed
with no extra work.

```
<instance>/profiles/<profile>/plugins.txt                 # live
<instance>/profiles/<profile>/plugins.txt.2026_10_02_08_45_55
<instance>/profiles/<profile>/loadorder.txt
<instance>/profiles/<profile>/loadorder.txt.2026_10_02_08_45_55
<instance>/profiles/<profile>/lockedorder.txt
<instance>/profiles/<profile>/lockedorder.txt.2026_10_02_08_45_55
<instance>/profiles/<profile>/modlist.txt
<instance>/profiles/<profile>/modlist.txt.2026_10_02_08_45_55
```

### Naming

`<live file name>.<yyyy_MM_dd_hh_mm_ss>`, exactly MO2's scheme
(`mainwindow.cpp:3830`). Local time, one stamp captured per user action and
shared by every file in it.

Keeping MO2's scheme rather than inventing a `backups/` subdirectory buys two
things for free: MO2 users' existing backups are visible to us, and the whole
feature is a file copy with no directory management.

If the computed stamp already exists, disambiguate by appending `-2`, `-3`
and so on. MO2 does not handle this and a same-second double click would
silently overwrite the first backup.

### Retention

Keep **10** newest per source file, matching `mainwindow.cpp:3834`. Exposed as
a setting (`backup/keep_count` in `ui::Settings`, which is the single QSettings
facade, `settings.h:16`) so a user with a busy profile can raise it.

Ordering is by the **parsed stamp**, not by raw name and not by mtime. MO2
sorts by name (`mainwindow.cpp:3834`), which works only because the stamp is
fixed-width and zero-padded; parsing it is the same amount of code and is
robust to a clock change. A candidate is eligible for eviction only if its
suffix parses as a stamp, which closes MO2's loose-glob hole
(`mainwindow.cpp:3823`).

Sweeping per source file, so a failure on `plugins.txt` cannot take
`loadorder.txt`'s history with it.

### Contents

| Artifact | Contains | Does not contain |
|---|---|---|
| Load-order backup | `plugins.txt` + `loadorder.txt` + `lockedorder.txt`, byte-for-byte | mod files, `archives.txt`, `settings.ini` |
| Mod-list backup | `modlist.txt`, byte-for-byte | mod files, profile selection, `archives.txt`, `settings.ini` |

## 4. Restore flow

1. **Anchor** on the live file. Enumerate `<anchor>.*` in the anchor's
   directory, regular files only.
2. **Classify** each suffix. Three outcomes, matching MO2
   (`mainwindow.cpp:3860-3881`): a valid stamp; a six-letter suffix, which is
   an orphaned atomic-write temporary and gets a warning; anything else, which
   is a hand-made copy. A stamp is valid when it is 19 characters of digits and
   underscores in the positions `yyyy_MM_dd_hh_mm_ss`. No regex needed.
3. **Sort newest first**, by parsed stamp. That is MO2's reverse-iteration
   behaviour (`mainwindow.cpp:3867`) with a real comparator.
4. **Present** via `ui::ListDialog` (`list_dialog.h:20`) with `setChoices` for
   the human-readable timestamp and `setChoiceData` for the raw stamp, so the
   restore path never re-parses a display string. Add the per-choice
   description line so the orphan-temporary warning survives.
5. **Zero candidates**: information dialog, `"There are no backups to
   restore"`, matching MO2's message (`mainwindow.cpp:3885-3886`). Return.
6. **Cancelled**: return, do nothing, report nothing. Same as MO2.
7. **Confirm before writing.** This is the deliberate divergence from MO2.
   MO2 overwrites silently (`mainwindow.cpp:3904-3906` passes `true`). Use
   `ui::TaskDialog` plus the existing `configure_*_dialog` shape
   (`mod_actions.h:19`), naming the files that are about to be replaced.
8. **Take a pre-restore safety backup first**, unconditionally, with the same
   stamp machinery. See section 6.1. This is what makes a wrong restore
   recoverable.
9. **Write atomically per file.** Read the backup's bytes, then
   `profile::safe_write_file(live_path, bytes)` (`safe_write_file.h`). A plain
   `copy_file` is not atomic and a crash mid-copy leaves a torn `plugins.txt`.
   The files are kilobytes; reading them into memory is free.
10. **Do not let in-memory state clobber the restore.**
    `ProfileManager` has a 5-second debounced writer (`profile.h:81`), so call
    `cancel_modlist_write()` (`profile.h:192`) before writing and re-read from
    disk after. A mod-list restore in particular must not be followed by a
    flush of the stale in-memory mod list.
11. **Reload.** Load-order restore: `load_profile()` then repopulate the
    plugin view and `refresh_counters()`, mirroring
    `mod_list_controller.cpp:3024-3030`. Mod-list restore: reload the
    `ProfileManager` state from the restored file, then
    `refresh_mod_status()` and repopulate the mod model.
12. **Report per file, not with one message.** MO2 collapses every failure into
    `"Failed to restore the backup. Errorcode: %1"`
    (`mainwindow.cpp:3910-3912`). Enumerate the failures that can actually
    occur here and give each its own line:

| Failure | Message |
|---|---|
| no backup exists for the chosen stamp for this file | `"No backup of <file> at <stamp>"`, file left alone |
| backup exists but is unreadable | `"Could not read the backup of <file>"` |
| profile directory is not writable | `"Could not write <file>: permission denied"` |
| write ran out of space or the rename failed | `"Could not write <file>"` plus the errno text |
| a malformed line was found while validating | `"<file> has invalid entries and was not restored"`, file left alone |

If any file failed, say so in those words, because after a partial restore the
profile is mixed and the user needs to know which half is stale. A restore in
which every file succeeded reports a transient success message carrying MO2's
wording (`mainwindow.cpp:3848`, `mainwindow.cpp:3923`).

## 5. Out of scope

Stated explicitly, because the obvious expansions are all wrong here.

- **Mod files and mod directories.** MO2's U034-U036 do not touch them. MO2's
  per-mod directory backup (`modlistviewactions.cpp:1041`) is a different
  feature with a different trigger and a different location, and GMM already
  has a mirror-and-backup path for external mods (`mod_actions.h:57`).
  If mod-file backup is wanted it is its own design, not a phase of this one.
- **`archives.txt` and `settings.ini`.** Real, but not what MO2 backs up, and
  not what this feature is for.
- **Compressing a backup set into one archive file.** MO2 does not. The
  format is a timestamped sibling.
- **An automatic backup before deploy, before a profile switch, on launch, or
  on exit.** MO2 has no such hook anywhere. Inventing one is a different
  decision about the user's disk and their deploy path, and it should be a
  separate, explicitly-agreed feature rather than padding added to match a
  section title.
- **The deploy `Original_Files` backup store.** That is a different directory,
  a different lifecycle, and a different meaning of the word backup
  (`deploy_utils.h:153-159`). The naming collision is worth a comment where the
  new code is added so a future reader does not merge the two.
- **Whole-instance snapshot or modpack export.** `InstanceSnapshot`
  (`instance_snapshot.h:4-5`) already does that, captures strictly more state,
  and is what modpack export/import uses. A second whole-instance mechanism
  would be a duplicate.
- **Restore into a different profile or a different instance.** MO2 anchors the
  picker on the live file's own name and directory (`mainwindow.cpp:3855`), so
  it structurally cannot. Cross-profile restore is a separate feature.

## 6. Risks

### 6.1 The big one: a bad restore breaks a working instance

A load order is the difference between a game that starts and one that does
not, and MO2 replaces it without asking and without keeping a copy
(`mainwindow.cpp:3904-3906`). Three mitigations, in order of value.

**Pre-restore safety backup. Mandatory, and it is cheap.** Before writing
anything, copy the current live files to the same stamp machinery, with a
stamp that cannot collide with the chosen one. About ten lines. After this,
the worst case is "the restore I just did was wrong", not "the state is gone".
MO2 omits it, and that omission is the single largest defect in this feature.

**Validate before writing, not after.** The realistic bad backup is a
truncated or half-written file from a crash, not a subtly wrong one. So:
refuse to write a backup whose `lockedorder.txt` has any unparseable line
(the loader already discards them at `plugin_database.cpp:1043-1050`, so count
the discards and compare against the line count), and refuse a `loadorder.txt`
or `plugins.txt` that yields materially fewer entries than the live file. A
half-written file is short; a legitimate one is not, unless mods were
uninstalled in between. This catches the case that matters and refuses nothing
legitimate.

**Fail per file, never all-or-nothing.** MO2's `||` chain
(`mainwindow.cpp:3904-3906`) means a failure on the first file leaves the
other two stale and unreported. Restore everything that validates, name
everything that does not.

### 6.2 In-memory state clobbers the restore within five seconds

`ProfileManager` debounces `modlist.txt` writes by 5s (`profile.h:81`) and
`Database` holds its own plugin order in memory. A restore that does not cancel
pending writes and re-read from disk is overwritten by the app's own writer
shortly after. MO2 has the mirror-image hazard: `refreshESPList` calls
`writeModlist()` before refreshing (`organizercore.cpp:1301`).

Mitigations: `cancel_modlist_write()` before writing, re-load after. Both
calls already exist (`profile.h:192`, `profile.h:168`).

### 6.3 Capturing a half-updated load order

MO2's flush is deferred: `savePluginList` registers an
`onNextRefresh(..., RUN_NOW_IF_POSSIBLE)` callback
(`organizercore.cpp:1976-1981`), so if a directory refresh is already running
the backup copies stale files. GMM's `Database::save_profile`
(`plugin_database.cpp:1079-1095`) is synchronous, so using it gets this right
for free. Use it, and do not reintroduce a deferred flush.

The separate question of backing up *during* a deploy is real. A 10-deep
history absorbs a bad backup, so this is a phase-4 concern, not a blocker.

### 6.4 Clock changes and daylight saving

The stamp is local time (`mainwindow.cpp:3844`). A backwards clock jump
produces a suffix that sorts before existing backups, so a name-ordered
"newest first" list shows the wrong entry and a name-ordered retention sweep
evicts from the wrong end. Parsing the stamp for both ordering and eviction
(section 3) removes the dependency on name order entirely. This costs nothing
and is why the design does not simply copy MO2's `QDir::Name`.

### 6.5 Retention deleting the wrong files

MO2's sweep matches a `?`-glob (`mainwindow.cpp:3823`) rather than its own
strict regex (`mainwindow.cpp:3824-3825`), so a file whose suffix happens to
have the right shape is eligible for deletion whether or not it is a real
backup. Restricting eviction to suffixes that parse as a stamp closes it.

### 6.6 The backup that silently did nothing

`Database::save_profile` returns `bool` and **every current call site ignores
it** (`mod_list_controller.cpp:3029`, `3035`, `3208`, `3230`, `3256`, `3275`).
A backup path that ignores its own copy result is a backup path that reports
success while having done nothing, which is worse than no feature. Every
`copy_file` and every `safe_write_file` result on this path is checked, and a
failure is reported with the filename.

### 6.7 Naming collision inside one second

Two backups in the same second produce the same destination. The second either
fails or overwrites the first, depending on the copy flags. Detect the existing
stamp and disambiguate (section 3).

## 7. Phasing

### Phase 1: engine, no UI

`src/engine/backup/backup_service.{h,cpp}`, Qt-free:

- `create_backup(ProfileManager &, BackupKind, now)` where `BackupKind` is
  `LoadOrder` or `ModList`
- `list_backups(anchor_path)` returning `vector<BackupEntry{stamp, path,
  orphan_flag}>`
- `restore_backup(anchor_path, stamp)` returning `vector<PerFileResult>`
- stamp validation, same-second disambiguation, the retention sweep, and the
  pre-restore safety backup

This is where every risk in section 6 lives, and it is the part that can be
tested without a GUI. Roughly 250 lines including the guards. **On its own it
ships nothing the user can reach**, which is fine: it is the half that is
worth getting right.

### Phase 2: the UI wiring, and the working feature

Four icon buttons beside the existing "Active:" counters (Plugins tab and Mods
tab), two `ListDialog` pickers, a `ui::TaskDialog` confirmation, per-file
failure reporting through `ui::report_error`, and a transient success message.
Roughly 150 lines.

**Phase 1 plus phase 2 is a complete, working, MO2-parity feature.** That is
the phase pair to schedule. Phase 1 alone is not worth shipping to a user.

### Phase 3: polish

- the per-choice description on the picker, so the orphan-temporary warning
  survives
- the transient info message, built once and shared with the notifications
  system that `featuremap.md` section 46 wants anyway
- the `backup/keep_count` setting and its dialog control
- the two icon keys and their assets

### Phase 4: optional, explicitly not MO2 parity

An automatic backup before deploy. MO2 has no such hook. Ship it only as its
own decision, with its own setting, and say plainly in the release notes that
it exceeds MO2.
